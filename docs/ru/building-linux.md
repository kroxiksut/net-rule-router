# Сборка из исходников (Linux)

[English](../en/building-linux.md) · **Русский**

Эта страница — для тех, кто хочет собрать NetRuleRouter под Linux сам. Сборка
под Windows описана [отдельно](building-windows.md); macOS — дальше по плану.

Поддержка Linux моложе, чем Windows: рабочее пространство собирается, тесты
проходят, служба применяет политику на живой машине — но готовой сборки пока
нет, поэтому всё ниже начинается с клона репозитория.

## Что установить

| Что | Версия | Зачем |
|-----|--------|-------|
| Git | любая свежая | клонировать репозиторий |
| [Rust (rustup)](https://rustup.rs/) | ставится через rustup | весь основной код |
| Компилятор C/C++ | gcc или clang | линковка и нативная часть Qt |
| Qt 6 | 6.6+ | графический интерфейс |
| CMake | 3.21+ | сборка нативной части Qt |
| `nftables` | любая текущая | через него служба применяет правила |

В Debian и Ubuntu это примерно так:

```bash
sudo apt install build-essential cmake nftables \
     qt6-base-dev qt6-declarative-dev
```

Версия тулчейна закреплена в `rust-toolchain.toml`, так что rustup скачает
нужную сам при первой сборке.

> В Debian и Ubuntu инструменты Qt 6 называются с суффиксом (`qmake6`,
> `qtpaths6`), чтобы стоять рядом с Qt 5. Сборка ищет оба написания; нужен ей на
> самом деле CMake-пакет Qt 6.

## Сборка

```bash
./scripts/bootstrap.sh          # проверяет окружение, создаёт .env, cargo check
./scripts/build.sh              # отладочная сборка
./scripts/build.sh --profile release
```

`bootstrap.sh --strict-qt` не предупреждает, а падает, если Qt или CMake не
найдены — это правильное поведение в CI, где отсутствие зависимости GUI должно
останавливать прогон, а не давать сборку без интерфейса.

Собрать вообще без Qt-хоста (служба, консоль и все библиотеки, но без GUI):

```bash
NRR_SKIP_QT_HOST=1 cargo build --workspace
```

Так делает CI, и это правильный ключ на машине без графики. Не выставляйте его,
если собираетесь запускать GUI: лаунчеру будет нечего запускать.

## Запуск

```bash
./scripts/run.sh --component gui
./scripts/run.sh --component tray
./scripts/run.sh --component service
```

Служба обычно живёт как systemd-юнит, а не запускается из терминала:

```bash
./scripts/install-service.sh            # собирает, раскладывает, включает и запускает
./scripts/service-status.sh             # что делают юнит и политика
./scripts/uninstall-service.sh
```

Перед регистрацией юнит раскладывается в `/usr/lib/netrulerouter`: он работает с
`ProtectHome=yes`, и демон, оставленный в `/home`, мог бы только падать на
запуске. Под `sudo` идут лишь копирование и регистрация — сборка остаётся
непривилегированной, чтобы в `target/` ничего не досталось root.

Интеграция с рабочим столом (пункт меню и значок) — это данные сеанса
пользователя, и ставится она отдельно:

```bash
./scripts/install-desktop.sh            # для себя
./scripts/install-desktop.sh --system   # для всех, нужен root
```

Пользовательский вариант запускайте от себя, а не через `sudo`: пути берутся из
вашего сеанса, а под `sudo` они разрешились бы для root.

## Гейт качества

```bash
bash scripts/check.sh --require-cargo-deny
```

Те же проверки и в том же порядке, что на Windows: форматирование, clippy с
запретом предупреждений, полный набор тестов, затем `cargo deny`. Тесты
энфорсмента, которым нужен root (nftables, живые маршруты), пропускают себя
сами и говорят об этом вслух.

Если вы разрабатываете под Windows, а Linux собираете в WSL, прогоняйте этот
гейт перед пушем: успешная сборка на одной платформе ничего не доказывает про
другую.

## Как удалить всё

```bash
./scripts/purge-data.sh                 # вхолостую: покажет, что удалил бы
./scripts/purge-data.sh --yes
```

Журнал аудита остаётся, пока не добавите `--purge-audit`. Где что лежит —
в [«Где NetRuleRouter хранит свои файлы»](where-files-live.md).
