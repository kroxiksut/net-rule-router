# Форматы файлов NetRuleRouter

[English](../en/rules-file-format.md) · **Русский**

Этот документ определяет все внешние форматы файлов, используемые
NetRuleRouter. Он охватывает формат текстового файла правил и формат YAML для
экспорта настроек.

## 1. Формат файла правил

**Краткая справка.** Всё, что может стоять в строке; подробности — в разделах
ниже.

| Что писать | Что значит | Пример |
|---|---|---|
| `--- Имя` | Заголовок секции: тип правил под ним (§1.2) | `--- Domains` |
| `значение` | Правило: отправлять это назначение маршрутом этого файла | `example.com` |
| `*.значение` | Сайт со всеми поддоменами | `*.example.com` |
| `значение.*` | Сайт в любой зоне | `example.*` |
| `!значение` | Запрет: не пускать это назначение ни через одно подключение (§1.12) | `!telemetry.example.net` |
| `?значение` | Маршрут этого файла, пока сайт через него открывается (§1.15) | `?accounts.example.com` |
| `# значение` | Правило сохранено, но выключено | `# example.com`, `# !example.com` |
| `значение  # текст` | Правило с вашей заметкой | `example.com  # обновления` |
| `значение +children` | Правило приложения, которое охватывает и запущенные им программы (§1.6) | `codex.exe +children` |
| `значение +override` | Правило программы, которое удерживает защита системных программ; применяется после вашего подтверждения (§1.16) | `!/var/www/* +override` |
| `# текст` | Комментарий, не читается как правило | `# мои заметки` |

`!` и `?` ставятся вплотную перед значением, у выключенного правила — после
`#`, и никогда вместе.

### 1.1 Обзор

Правила маршрутизации хранятся в простых текстовых файлах — по одному файлу на
роль маршрута. Пользователь выбирает имя файла; приложение сохраняет
настроенный путь в настройках интерфейса. Типичные имена — `rules_primary.txt`
и `rules_secondary.txt`, но принимается любое допустимое имя файла.

Файлы удобны для чтения человеком и могут редактироваться в любом текстовом
редакторе. Интерфейс читает и пишет одни и те же файлы; правки из обоих
источников семантически эквивалентны.

Когда пользователь меняет настроенный путь на другой файл, кэш правил SQLite
очищается и перезагружается из нового файла перед вступлением изменения в силу.

### 1.2 Секции

Файл правил организован в именованные секции. Каждая секция группирует правила
одного типа. Имена секций — **технические ключевые слова** — они никогда не
локализуются и должны отображаться точно так, как показано.

#### Поддерживаемые секции

| Заголовок секции | Тип правила | Платформы |
|---|---|---|
| `--- Zones` | Маршрутизация группы уровня зоны | Все |
| `--- Domains` | Суффиксные и точные правила FQDN | Все |
| `--- IP` | Правила точного IP-адреса | Все |
| `--- CIDR` | Правила подсетей (`10.0.0.0/8`) | Все |
| `--- Ranges` | Правила диапазонов IP (`192.0.2.10-192.0.2.40`) | Все |
| `--- Windows` | Правила приложения Windows (имя `.exe`, путь к файлу или папка) | Только Windows |
| `--- Linux` | Правила приложения Linux (имя процесса, путь к файлу или папка) | Только Linux |
| `--- MacOS` | Правила приложения macOS (имя процесса, путь к файлу или папка) | Только macOS |
| `--- Auto` | Правила, добавленные самим приложением (§1.13) | Все |

Будущие версии могут вводить дополнительные секции (например, `Ports`) по мере
расширения модели правил.

Секции пишутся в порядке таблицы выше, включая пустые (см. «Пустые секции»
ниже). `--- Auto` пишется последним, так что файл читается как «правила, которые
вы написали, затем правила, добавленные приложением для вас».

**Секция — это строго тип.** Значение, записанное как другой тип, — ошибка
строки, и сообщение называет секцию, в которой ему место: подсеть или диапазон
в `--- IP`, адрес в `--- CIDR`, программа (`chrome.exe`, путь) в `--- Domains`
или `--- Zones`, адрес, сеть или домен в `--- Windows`, адрес или сеть в
`--- Linux` / `--- MacOS`. Одно слово (`telegram`, `ru`) может быть и зоной, и
программой, поэтому решает секция. В Linux и macOS в имени программы бывают
точки, поэтому имя с точкой там принимается. Сама программа никогда не
переносит строки между секциями: она предлагает перенести строку и переносит,
только когда вы подтвердите.

#### Фильтрация по платформе

`--- Windows`, `--- Linux` и `--- MacOS` зависят от платформы. На хосте Windows
секции Linux и macOS **парсятся и сохраняются** в файле, но не применяются к
политике маршрутизации. Интерфейс скрывает их по умолчанию. Параметр
«Показывать правила для других операционных систем» делает их видимыми.

Это позволяет обмениваться одним файлом правил между платформами (или
подготовить его заранее для будущей платформы) без разделения файлов.

#### Пустые секции

Секции без записей пишутся при экспорте и не должны удаляться. Они резервируют
место в файле для будущего использования и делают структуру файла
самодокументирующейся.

### 1.3 Синтаксис

#### Заголовок секции

```
--- SectionName
```

Ровно три дефиса, один пробел, затем имя секции. Замыкающие пробельные символы
игнорируются. Имя чувствительно к регистру.

#### Активное правило

```
example.com
```

Строка, которая не является комментарием и не является заголовком секции, — это
активное правило. Значение совпадения — вся строка, очищенная от ведущих и
замыкающих пробельных символов.

#### Активное правило со встроенным комментарием

```
example.com  # обновления поставщика домен
```

Текст после `#` в строке без комментария — это встроенный комментарий. Он
отображается как метка/описание в списке правил интерфейса и сохраняется при
экспортах. `#` и всё, что после него, не являются частью значения совпадения.

Комментарий начинается с `#`, перед которым стоит пробел или табуляция. `#`
внутри значения остаётся его частью, так что `C:\Projects\C#\tool.exe` называет
именно эту программу. Программа, в имени которой `#` стоит сразу после пробела,
записывается в двойных кавычках (`"C:\Tools\Build #2\tool.exe"  # заметка`), тех
же, что описаны ниже.

**Ограничение длины встроенного комментария: 200 символов** (после разделителя
`#`, очищенного от ведущих/замыкающих пробельных символов). Диалог
добавления/редактирования правил интерфейса обрезает ввод на этом ограничении и
показывает счётчик `использовано/макс`. Парсер файла правил
отклоняет записи, у которых встроенный комментарий превышает 200 символов, с
ошибкой валидации, так что формат на диске и интерфейс согласованы. Строки
свободных комментариев (отдельный `# …`) не подчиняются этому ограничению,
потому что они не привязаны к правилу.

#### Отключённое правило

```
# example.com
# codex.exe +children
```

`#` в начале строки, за которым следует допустимое значение правила, отмечает
правило как **отключённое**. Интерфейс представляет это как правило с
выключенным переключателем. Отключение правила в интерфейсе комментирует его
строку; включение удаляет `#`.

Строка, начинающаяся с `#`, где остальное не является допустимым значением
правила (например `# это примечание`), рассматривается как свободный
комментарий — она не показывается как отключённое правило в интерфейсе.

В секции приложений программа, записанная в двойных кавычках, всегда
правило, включённое или нет, а кавычки не входят в её имя. Так приложение
записывает отключённую программу, имя которой иначе читалось бы как
примечание, поэтому отключение её не теряет:

```
# "Web Content" +children   # примечание
```

Если убрать `#` вручную, правило включится; кавычки можно оставить. `!` ставится
перед открывающей кавычкой, а `+children` или `+override` — после закрывающей.

#### Проверить, где работает

```
?accounts.example.com
?*.mail.example.net
?203.0.113.7
# ?old.example.com
```

`?` непосредственно перед доменным значением или отдельным IPv4-адресом, в любом
из двух файлов, просит приложение проверить, что сайт открывается через
маршрут этого файла (§1.15). У отключённого правила `?` ставится после `#`, а
не перед ним.

#### Запрет

```
!telemetry.example.net
!10.20.0.0/16
!telemetry.exe
# !old.example.com
```

`!` вплотную перед значением, в любом из двух файлов и в любой секции,
запрещает назначение: его не пускают ни через одно подключение (§1.12). У
отключённого правила `!` ставится после `#`; вместе с `?` не пишется.

#### Свободный комментарий

```
# Это свободный комментарий, а не правило.
```

Отдельные строки комментариев (где содержание после `#` не является узнаваемым
значением правила) игнорируются механизмом правил и не показываются в списке
правил интерфейса.

Когда файл пишет программа, они **не сохраняются**. Сохранение правил из окна,
трея или терминального интерфейса пишет файл заново по списку правил, а
свободного комментария в этом списке нет. Заметку, которую нужно сохранить,
пишите в строке самого правила (`example.com  # зачем оно здесь`): это
комментарий правила, и он записывается вместе с правилом, если только при
выгрузке не выключено «Включить комментарии к правилам». Секции других
операционных систем записываются обратно как были. Файл, который вы правили
руками после последнего сохранения программой, не перезаписывается: программа
оставляет его как есть и предлагает сравнить с действующими правилами.

#### Подсказка по синтаксису

```
#: !значение           запрет: ни через одно подключение    !ads.example.net
#: ?значение           этот маршрут, пока сайт открывается  ?mail.example.com
```

Файл, который пишет программа, начинается с нескольких строк с `#:`, где
кратко собран этот синтаксис. Они пишутся заново при каждом сохранении, на
языке интерфейса в этот момент, и программа их никогда не читает: правка этих
строк ничего не меняет. Не начинайте свои строки с `#:` — они пропадут вместе
с подсказкой. Версия формата из-за подсказки не меняется: старая сборка читает
её как комментарии.

#### Пустые строки

Пустые строки и строки, содержащие только пробельные символы, игнорируются.

### 1.4 Полный пример

```
# NetRuleRouter файл правил — версия 11
# Маршрут: Основной (основная сеть)

--- Zones
*.ru           # весь трафик TLD .ru
corp-internal  # внутренняя корпоративная зона

--- Domains
updates.example.org    # точный FQDN: точка обновления поставщика
*.corp.example.net     # все поддомены corp.example.net
# *.old.example.com    # отключено: выведенный из эксплуатации диапазон поддоменов
?accounts.example.com  # через основной, пока открывается через него (§1.15)

--- IP
203.0.113.7

--- CIDR
10.0.0.0/8             # корпоративная сеть
2001:db8::/48

--- Ranges
192.0.2.10-192.0.2.40  # блок адресов

--- Windows
browser.exe        # трафик браузера
*vpn*.exe          # любой исполняемый файл VPN-клиента
C:\Tools\Sync\*    # все программы папки и её подпапок
# powershell.exe   # временно отключено

--- Linux
# (зарезервировано — не применяется в Windows)

--- MacOS
# (зарезервировано — не применяется в Windows)

--- Auto
rr3.example-cdn.net  # auto:site-companion anchor:example.org added:2026-07-31
```

Файл дополнительного маршрута из той же пары:

```
# NetRuleRouter файл правил — версия 11
# Маршрут: Дополнительный (VPN)

--- Domains
*.streaming.example.com    # всегда через VPN
?*.video.example.net       # через VPN, пока открывается через него (§1.15)
example-tv.*               # сайт во всех зонах (§1.5)
!telemetry.example.net     # не покидает этот компьютер (§1.12)
```

### 1.5 Приоритет оценки правил

Побеждает более узкое правило. Порядок фиксирован (от наивысшего к
наинизшему), правила обоих файлов оцениваются вместе:

1. **Точный домен** — `example.com` (без префикса `*.`) совпадает только с
   этим именем хоста.
2. **Домен с поддоменами** — `*.example.com` совпадает с самим `example.com` и
   любым его поддоменом на любой глубине. Среди конкурирующих суффиксных правил
   побеждает самый длинный базовый домен. Чтобы направить апекс иначе, чем его
   поддомены, добавьте точное правило для апекса — оно уровнем выше и побеждает.
3. **Сайт в любой зоне** — `example.*` совпадает с `example.com`, `example.net`,
   `example.co.uk` и любыми их поддоменами: для каждого хоста это правило
   `*.example.<зона>`. Правило с явной зоной (`example.by`, `*.example.by`)
   сильнее его на любом маршруте; из двух таких правил побеждает более длинное
   имя, так что `mail.example.*` сильнее `example.*`.
4. **IP** — `203.0.113.7`, один точный адрес. Побеждает любую сеть, в которую
   входит.
5. **CIDR и Ranges** — `10.1.0.0/16` или `192.0.2.10-192.0.2.40`. Из двух сетей
   побеждает более длинный префикс, так что `10.1.0.0/16` побеждает
   `10.0.0.0/8`. Одна и та же сеть на обоих маршрутах — ошибка.
6. **Zones** — `ru` совпадает с каждым именем хоста, оканчивающимся на `.ru`.
   Более длинная зона побеждает более короткую. Сеть или точный адрес внутри
   зоны побеждают зону.
7. **Приложение** — `chrome.exe`, `C:\Apps\Tool\tool.exe`, `C:\Apps\*`
   (`Windows` / `Linux` / `MacOS`). Внутри уровня побеждает более узкое
   правило: сначала полный путь, затем точное имя, затем папка (более глубокая
   раньше; на одной глубине «только эта папка» раньше, чем «с подпапками»),
   затем шаблон имени; среди нескольких совпавших шаблонов имени побеждает
   первое правило в файле. Оценивается только раздел своей платформы.
   Назначения, которым правило приложения учит маршрутизатор (§1.10),
   оцениваются на этом же уровне, поэтому правило адреса для того же адреса
   побеждает.
8. **Маршрут по умолчанию** — одноимённая настройка: основное или
   дополнительное подключение (см. [Быстрый старт](quickstart.md#первая-настройка)).

Правила имён (уровни 1, 2, 3 и 6) действуют, только когда имя назначения известно.

Остальное решают ещё два правила:

- Запрет (`!`, §1.12) точного IP-адреса останавливает этот адрес, какое бы
  правило его ни называло. Любой другой запрет стоит на своём уровне в порядке
  выше, так что запрет зоны не останавливает сайт, который направляет точное
  правило.
- Если два правила одного уровня одинаково конкретны, запрет сильнее
  маршрута, а основной маршрут — дополнительного.

По умолчанию правило для сайта или адреса сильнее правила для программы.
Переключатель **Программы из правил забирают весь свой трафик** (Настройки →
Маршрутизация) меняет это для программ: программа, указанная в правиле,
отправляет всё, к чему подключается, маршрутом этого правила — даже на сайты,
которые другое правило ведёт другой дорогой. Маршрут выбирается по адресу,
поэтому такой сайт пойдёт этим маршрутом у всех программ компьютера, а не
только у указанной. Запрет точного IP-адреса по-прежнему
останавливает свой адрес, а сайт, который называет основной маршрут, остаётся
доступен другим программам, когда дополнительный маршрут недоступен.
Переключатель по умолчанию выключен.

### 1.6 Отслеживание дочерних процессов (`+children`)

> **Пока не действует.** Эта версия принимает флаг и сохраняет его в правилах,
> но правило касается только названной программы; запущенные ею программы
> подчиняются своим правилам. Окно и терминальный интерфейс помечают такое
> правило предупреждением. Правило для запускаемых программ — в
> [планах развития](../../ROADMAP_RU.md).

По умолчанию правило приложения совпадает только с названным процессом.
Добавление флага **`+children`** после имени процесса расширяет правило на
**все дерево потомков** названного процесса — каждого дочернего процесса, внука
и так далее. Инструмент, который запускает вспомогательные программы
(`codex.exe` запускает `node_repl.exe`, `powershell.exe`, хост консоли
`conhost.exe` и т.д.), затем маршрутизирует назначения всего дерева под одним
правилом:

```
--- Windows
codex.exe +children
```

Флаг — это один разделённый пробельными символами токен после имени процесса и
перед любым встроенным комментарием `#` (`codex.exe +children  # помощник ИИ`).
Это флаг **для каждого правила** — он заменяет прежний глобальный параметр
«применять правила к дочерним процессам», который не мог выразить *какие*
дочерние процессы приложения отслеживать.

Атрибуция — по **дереву процессов, а не по имени процесса**: отдельный
`powershell.exe`, который **не** является потомком `codex.exe`, — это другое
дерево и *не* охватывается `codex.exe +children`. Правило поэтому никогда
случайно не маршрутизирует каждый PowerShell (или каждый `conhost.exe`) на
машине — только те, которые codex действительно запустил.

> Атрибуция дерева требует, чтобы уровень маршрутизации отслеживал живое
  происхождение процесса (`pid → ppid → image`) и знал PID, стоящий за каждым
  наблюдаемым подключением. Это проблема наблюдения/runtime, а не часть формата
  файла; она рассмотрена в проектных заметках вне этого документа.

**Инвариант приоритета:** явное правило для дочернего процесса всегда имеет
приоритет над маршрутизацией, унаследованной от совпадения родительского
процесса. `+children` никогда не переопределяет прямое правило для дочернего
процесса.

> Запрет (`!`, §1.12) сочетается с флагом: `!codex.exe +children`.

Флаг имеет смысл только после имени программы. После любого другого
значения он при чтении отбрасывается, и правило читается без него.
Выключенное правило программы сохраняет флаг: `# codex.exe +children`.

**Состояние в этом выпуске:** флаг принимается и игнорируется. Правило с
`+children` читается как обычное правило приложения и покрывает только
названный процесс; дерево потомков пока не отслеживается. Написать его сейчас
ничего не стоит — оно заработает, когда появится атрибуция по дереву процессов.

### 1.7 Имена секций не локализуются

Имена секций (`Zones`, `Domains`, `IP`, `CIDR`, `Ranges`, `Windows`, `Linux`,
`MacOS`, `Auto`) — технические ключевые слова в формате файла. Они не передаются через уровень
локали и не переводятся. Это применяется и к слагам причин, используемым внутри
секции `--- Auto` (§1.13): слаг в файле — фиксированное ключевое слово, и
интерфейс отображает переведённое предложение для него.

Интерфейс может отображать локализованные описания *о* каждой секции
(показанные как подсказки или всплывающие подсказки), но имя секции, записанное
в файл, всегда это канонический английский ключевое слово.

Пользовательские встроенные комментарии (после `#`) — личные заметки на
выбранном пользователем языке — они никогда не модифицируются или не
переводятся.

### 1.8 Синтаксис значения совпадения

Каждая секция принимает конкретные паттерны значений совпадения. Значения вне
принятого синтаксиса производят семантическую ошибку валидации — правило
отклоняется с чётким сообщением.

#### Zones (`--- Zones`)

| Пример | Значение |
|---|---|
| `corp-internal` | Названная внутренняя зона |
| `*.ru` | Все домены под TLD `.ru` |
| `ru` | Каноническая форма — парсер нормализует `*.ru` и `ru` оба в `ru` |

Имена зон приводятся к нижнему регистру при чтении. Оба `*.ru` и `ru` приняты
как ввод и сохранены в каноническом виде как `ru`. Имя зоны должно состоять из
допустимых символов DNS-метки (буквы, цифры, дефисы, точки для составных зон,
таких как `corp.internal`). Пробелы не допускаются.

#### Domains (`--- Domains`)

| Пример | Значение | Уровень приоритета |
|---|---|---|
| `example.com` | Точный FQDN — совпадает только с `example.com` | Точный домен (уровень 1) |
| `*.example.com` | Суффикс — совпадает с `example.com` и любым поддоменом его на любой глубине | Домен с поддоменами (уровень 2) |
| `example.*` | Сайт в любой зоне — `example.com`, `example.net`, `example.co.uk` и их поддомены | Сайт в любой зоне (уровень 3) |

Префикс `*.` — это явный оператор поддомена. Голое имя домена без `*.`
совпадает только с точным FQDN. Две формы ортогональны: хост совпадает на
уровне 1 своей точной записью; он переходит на уровень 2 только если правило
суффикса его охватывает.

Поскольку уровень 1 проверяется первым, написание обеих форм — вот как вы
разделяете сайт: `*.example.com` на одном маршруте и `example.com` на другом
отправляют поддомены одним способом и голый домен другим.

`example.*` нужен для сайта, который живёт в нескольких зонах: одна строка
заменяет `example.com`, `example.net` и остальные. Зона — это конец имени
хоста, под которым продают домены, — `com`, `ru` или из двух частей, как
`co.uk`, — поэтому `example.com.other.net` принадлежит `other.net` и не
совпадает. `*.example.*` читается как то же правило. Чтобы отправить одну зону
сайта другим путём, добавьте правило для неё (`*.example.by`): правило с явной
зоной всегда сильнее. Проверка `?` (§1.15) нужна для одного хоста и к
`example.*` не применяется.

#### IP (`--- IP`)

Точный адрес IPv4 или IPv6, по одному в строке.

```
203.0.113.7
2001:db8::7
```

Подсеть или диапазон сюда не записываются: это ошибка строки, и сообщение
называет секцию, в которой им место (`--- CIDR` или `--- Ranges`).

> Не путайте эти секции со списком **«Локальные сети»** в настройках. У того
> списка другая задача: он называет локальные сетевые сегменты — например, сеть
> виртуальных машин гипервизора или подсеть вашего основного подключения, —
> которые должны оставаться доступными, пока маршрутизируемый трафик
> заблокирован. Он никуда не отправляет трафик — он лишь сохраняет доступность
> локальных сегментов.

#### CIDR (`--- CIDR`)

Подсеть в нотации CIDR, IPv4 или IPv6, по одной в строке. Целая сеть
направляется одним правилом, в Windows и Linux.

```
10.0.0.0/8             # корпоративная сеть
2001:db8::/48
```

#### Ranges (`--- Ranges`)

Диапазон адресов включительно, `первый-последний`, IPv4 или IPv6. Пробелы
вокруг дефиса при чтении допускаются; при записи файл пишется без них.

```
192.0.2.10-192.0.2.40
192.0.2.100 - 192.0.2.120
```

#### Что приложение проверяет в сети или диапазоне

- Подсеть шире /8 (IPv4) или /16 (IPv6) отклоняется, чтобы одно правило не
  захватило заметную долю интернета.
- Подсеть или диапазон, затрагивающие loopback, multicast, broadcast или блок
  «эта сеть», отклоняются.
- Link-local адреса принимаются с предупреждением.
- Установленные биты хоста в подсети (`10.0.2.7/24`) сбрасываются с
  предупреждением, и файл записывается как `10.0.2.0/24`.
- Одна и та же сеть на обоих маршрутах — ошибка строки.
- При сохранении сеть отклоняется, если покрывает адрес сервера туннеля, сеть,
  к которой подключён компьютер, или пул адресов, который приложение использует
  для маршрутизации по именам. Сообщение называет, что именно она покрывает.
- Сеть шире /16 (IPv4) или /48 (IPv6) маршрутизируется, но пока дополнительное
  подключение недоступно, защита от утечки в варианте **«Только сайты из
  правил»** её не задерживает; при сохранении правила приложение предупреждает
  об этом.

Вкладка «Пересечения» на экране правил показывает, когда адрес, названный для
основного подключения, лежит внутри сети, названной для дополнительного: этот
адрес остаётся на основном подключении, даже когда дополнительное недоступно.

#### Windows / Linux / MacOS (секции приложений)

Программа задаётся именем файла, шаблоном имени или местом, где она лежит:
один файл, программы одной папки или программы папки и всех папок внутри неё.
Значение без разделителя пути — имя; значение с разделителем (`\` или `/` в
Windows, `/` в Linux и macOS) — путь.

| Пример | Совпадение |
|---|---|
| `chrome.exe` | Программа с этим именем, где бы она ни была установлена |
| `*vpn.exe` | Любая программа, имя которой заканчивается на `vpn.exe` |
| `nord*` | Любая программа, имя которой начинается с `nord` |
| `*vpn*.exe` | Любая программа, имя которой содержит `vpn` и заканчивается на `.exe` |
| `C:\Apps\Tool\tool.exe` | Этот один файл программы |
| `C:\Apps\Tool` или `C:\Apps\Tool\` | Программы прямо в этой папке, без подпапок |
| `C:\Apps\Tool\*` | Программы этой папки и всех папок внутри неё |
| `/opt/tool/bin/tool` | Этот один файл программы, а если это папка — её программы |
| `/opt/tool/` | Программы прямо в этой папке |
| `/opt/tool/*` | Программы этой папки и всех папок внутри неё |
| `%LOCALAPPDATA%\Discord\*` | У каждого пользователя — программы его собственной папки `AppData\Local\Discord` и папок внутри неё |
| `~/apps/*` | У каждого пользователя — программы папки `apps` в его домашней папке и папок внутри неё |

Правило папки удобно для программы, у которой рядом или в подпапках лежат
свои исполняемые файлы (помощники, обновлятель, новая папка версии после
каждого обновления): одно правило охватывает их все.

Правило папки не разделяет сайты, которые обслуживает один общий сервер,
например `php-fpm`, IIS или менеджер процессов Node.js: соединения сайтов
открывает сервер, а не файлы в папке каждого сайта, поэтому все сайты этого
сервера идут его маршрутом.

Шаблоны имени:

- `*` совпадает с **нулём или более символов** (любой символ, включая `.` и
  `-`). Это единственный подстановочный знак: `?` особого смысла не имеет.
- Голая `*` как всё значение совпадения — это **ошибка валидации** — слишком
  широкая, совпадала бы с каждым работающим процессом.
- Совпадение **не чувствительно к регистру** на всех платформах:
  `Telegram.exe`, `telegram.exe` и `TELEGRAM.EXE` обозначают одну программу.

Пути:

- Путь начинается с диска (`C:\`), сетевой папки (`\\server\share\`) или, в
  Linux и macOS, с `/`. Относительный путь (`Tools\tool.exe`, `bin/tool`) или
  путь с `..` — ошибка строки.
- `*` в пути допустима только как вся последняя часть, `\*` (или `/*`):
  «эта папка с подпапками». В любом другом месте пути (`C:\Apps\*.exe`,
  `C:\*\tool.exe`) это ошибка строки; чтобы задать программы шаблоном,
  напишите шаблон имени без пути.
- В Windows путь без `\` в конце — файл программы, если его последняя часть
  оканчивается на `.exe`, иначе папка. В Linux и macOS путь без `/` в конце —
  то, что лежит по нему, когда правило применяется: файл программы или папка.
  Чтобы прямо сказать «папка», допишите `/` в конце.
- Пути Windows и macOS сравниваются без учёта регистра; пути Linux — точно,
  как Linux называет файлы.
- Одна и та же папка в одном виде («только эта папка» или «с подпапками») в
  обоих файлах — ошибка, как одна сеть на обоих маршрутах.
- `!` перед путём запрещает программы, которые он задаёт; `+children` после
  него распространяет правило на программы, которые они запускают.
- В Windows и Linux правило папки охватывает и программу, которая появилась
  в папке позже, например папку новой версии после обновления, без
  перезапуска. Папка, в которой программ больше, чем охватывает одно правило,
  охвачена частично, и вкладка «Перекрытия» об этом говорит.
- В Windows и Linux правило папки охватывает и скрипты, лежащие в папке,
  когда их запускает интерпретатор, установленный в другом месте:
  `python tool.py`, `powershell -File job.ps1`, файл `.bat`, `.cmd` или
  `.vbs`, `java -jar app.jar` или путь классов Java в эту папку, а в Linux —
  скрипт со строкой `#!` или с битом исполнения. Запуск через «Выполнить с
  помощью PowerShell» в Проводнике тоже считается. Такой скрипт идёт по
  правилу, как только замечено его первое соединение. В Windows скрипт,
  который запускает служба или задание планировщика, идёт по правилам пользователя,
  чьи маршруты использует машина; скрипт, запущенный другим вошедшим
  человеком, вашему правилу папки не засчитывается.
- Программа, которая только открывает файл из папки, например редактор,
  правилом не охватывается, как и код, переданный прямо в командной строке
  (`bash -c "…"`, `-Command` PowerShell, который делает что-то кроме вызова
  одного скрипта). В Windows путь классов Java, заданный только переменной
  `CLASSPATH`, не распознаётся.
- Запрет папки останавливает программы из неё, но не гарантированно —
  скрипт из неё, который запускает интерпретатор, установленный в другом
  месте. Используйте его, чтобы остановить программы папки, а не как
  гарантию, что ничто запущенное из папки не пройдёт.
- Папка, в которую ведёт ссылка или точка соединения, оценивается там, где
  она на самом деле: ссылка в системную папку не применяется, как и сама
  системная папка.
- Путь может начинаться с папки собственного профиля пользователя:
  `%LOCALAPPDATA%`, `%APPDATA%` или `%USERPROFILE%` в Windows, `~` в Linux и
  macOS. В файле он хранится как написан и у каждого пользователя означает его
  собственную папку, поэтому одно правило общей конфигурации охватывает копию
  программы у каждого. Любая другая переменная (`%TEMP%`, `$HOME`, `~имя`) —
  ошибка строки.
- Правило одного пользователя никогда не охватывает программы в профиле
  другого пользователя. Новое правило с полным путём к папке в профиле
  другого пользователя отвергается; общая конфигурация задаёт папку
  пользователя только от папки профиля, как выше. Такая строка, уже записанная
  в файле правил, остаётся в нём, а вкладка «Перекрытия» показывает её как не
  применённую, с причиной.
- Для папки, куда может писать кто угодно (`C:\Users\Public`, большая часть
  `C:\ProgramData`, `/tmp`, `/var/tmp`, `/dev/shm`), при вводе правила
  показывается предупреждение: сюда кто угодно может положить программу.
  Программа из такой папки никогда не исключается из защиты от утечки, даже
  после вашего подтверждения.
- macOS пока не применяет правила по пути: такое правило остаётся в файле и
  в списке правил, а вкладка «Перекрытия» показывает его как не применённое,
  с причиной.

Приоритет в рамках уровня приложения, от самого узкого: полный путь, точное
имя, папка (более глубокая раньше; на одной глубине «только эта папка»
раньше, чем «с подпапками»), шаблон имени. Среди нескольких шаблонов имени,
совпавших с одной программой, побеждает первое определённое в файле правило.

#### Системные программы

Запрет (`!`) или правило в файле дополнительного маршрута не может называть
программу, без которой система теряет сеть, вход или точное время: в Windows
это, среди прочих, `svchost.exe`, `lsass.exe`, `services.exe`, `csrss.exe`,
`wininit.exe`, `smss.exe` и `winlogon.exe`; в Linux — службы `systemd`,
`NetworkManager`, `dhclient` и `wpa_supplicant`; в macOS — `launchd`,
`mDNSResponder` и `configd`. Это касается и маски, которая захватила бы одну из
них (`svc*.exe`), и собственных программ приложения. Основной маршрут называть
их может: этим путём они и так выходят в сеть.

Окно добавления правила отклоняет такое правило до сохранения. Правило, уже
записанное в файл правил, — вручную или оставшееся от прежней версии —
остаётся в файле и в списке правил, показывается как неприменённое с причиной
и не выполняется, пока его не изменят.

Если вы действительно этого хотите, допишите `+override` после значения:
тогда правило применяется после вашего подтверждения (§1.16). Корень диска и
собственные программы приложения подтвердить нельзя никогда.

### 1.9 Прямая совместимость — расширенные секции

Когда файл правил содержит секции, которые эта версия не узнаёт (например `--- Ports`, произведённая более новой версией или расширенным
форматом), эти секции **парсятся и сохраняются** в файле, но **не применяются**
к политике маршрутизации. Это зеркалирует существующее поведение для секций,
специфичных для платформы, на не совпадающем хосте (см. раздел 1.3).

В интерфейсе правила, принадлежащие неузнанным секциям, показываются с бейджем
«Не применяется». Они не могут быть переключены или отредактированы.

При экспорте неузнанные правила пишутся обратно в файл без изменений, поэтому
никакая информация не теряется, когда файл проходит через эту версию.

### 1.10 Правила приложений и назначения, которые они маршрутизируют

Маршрутизация **основана на назначении**: маршрут задаётся удалённым адресом, а
не процессом-источником. Поэтому правило приложения само по себе не может
отправить трафик процесса через дополнительный адаптер. Оно говорит другое: за
каким приложением следить. Назначения, к которым это приложение обращается,
распознаются по наблюдению и при последующих подключениях идут по маршруту
правила — то есть по маршруту того файла, в котором правило живёт
(`rules_primary.txt` или `rules_secondary.txt`).

> Настоящая *изоляция* по процессу (когда через дополнительный маршрут идёт
> трафик к общему адресу только **этого** приложения, а другие приложения,
> обращающиеся к тому же адресу, — нет) требует драйвера ядра и пока вне
> области работ. Назначение, распознанное от приложения, — обычный маршрут по
> адресу: он действует везде, где к этому адресу обращаются. Первое подключение
> к адресу, которого маршрутизатор ещё не видел, уходит обычным маршрутом;
> маршрутизация вступает в силу со следующего подключения.

В файле правило приложения — это **имя процесса на отдельной строке**:
вложенного синтаксиса для его назначений нет, а распознанные назначения — это
состояние времени выполнения, а не часть файла. Чтобы направить один конкретный
адрес независимо от того, какая программа к нему обращается, запишите его
обычным правилом в секции `--- Domains` или `--- IP`: эти ярусы старше яруса
приложений (§1.5), поэтому явное правило всегда побеждает то, чему приложение
научило маршрутизатор.

### 1.11 Версия формата

Строка заголовка `# NetRuleRouter файл правил — версия N` (и заголовок пресета
`# NetRuleRouter пресет — версия N`, §3.2) несёт версию формата файла.

| Версия | Добавляет |
|---|---|
| 1 | Секции, правила верхнего уровня, встроенные комментарии, отключённые правила. |
| 2 | Зарезервирована, не используется. |
| 3 | Флаг `+block` для каждого правила; в версии 9 заменён на `!`. |
| 4 | Секция правил, добавленных приложением (§1.13, `--- Auto`). |
| 5 | Секции подсетей и диапазонов (§1.8, `--- CIDR`, `--- Ranges`). |
| 6 | Префикс `?` у доменных правил в файле дополнительного маршрута (§1.15). |
| 7 | Префикс `?` у отдельных IP-адресов и в файле основного маршрута (§1.15). |
| 8 | Сайт в любой зоне (§1.8, `example.*`). |
| 9 | Запрет пишется `!` перед значением (§1.12); флага `+block` из версии 3 больше нет. |
| 10 | Приложение по пути: один файл, папка, папка с подпапками (§1.8). |
| 11 | `+override` после значения правила программы (§1.16). |

Версия 2 была зарезервирована под вложенный синтаксис `- destination` внутри
правил приложений. Он не был реализован, ни одна сборка его не читает и не
пишет; номер оставлен занятым, а не переиспользован, чтобы файл из любой сборки
означал во всех сборках одно и то же. Не объявляйте версию 2 в файле.

Файл, использующий `+override`, заявляет **версию 11**. Более старая сборка
читает флаг как часть значения и не применяет правило; остальной файл
работает.

Файл, задающий приложение путём, заявляет **версию 10**. Более старая сборка
читает путь к файлу там как одно имя программы и не применяет правило папки;
откройте такой файл в текущей сборке.

Файл, использующий `!`, заявляет **версию 9**. Строка, в которой остался
`+block`, — ошибка строки, сообщение показывает запись через `!`; как маршрут
она не читается никогда.

Файл, использующий `example.*`, заявляет **версию 8**. Более старая сборка
читает такую строку как домен, который не может принять, и не применяет её;
остальной файл работает.

Файл, использующий префикс `?`, заявляет **версию 7** (версию 6, если `?`
стоит только у доменных правил файла дополнительного маршрута). Сборка
версии 6 читает строку с `?` в файле основного маршрута как обычное правило
этого файла и не применяет правило с `?` у IP-адреса; более старая сборка
префикса не знает вовсе и такие правила не применяет. Открывайте такой файл в
актуальной сборке.

Файл, содержащий секцию `--- CIDR` или `--- Ranges`, заявляет **версию 5**.
Более старая сборка считает эти секции расширенными (§1.9): она сохраняет
правила в файле, предупреждает о них и не применяет, так что открытие такого
файла в старой сборке ничего не ломает.

Файл, содержащий секцию `--- Auto`, заявляет **версию 4**. Читатель до версии 4
не знает такого имени секции и потому считает её расширенной (§1.9): правила
сохраняются при проходе туда-сюда, но не применяются — ничего не теряется и
ничто не истолковано неверно.

### 1.12 Запрет (`!`)

По умолчанию правило *маршрутизирует* своё назначение через подключение,
привязанное к файлу, в котором живёт правило (`rules_primary.txt` → основной,
`rules_secondary.txt` → дополнительный; §1.10). **`!`** вплотную перед значением
вместо этого **запрещает** назначение: к нему ничего не отправляется ни через
одно подключение, включая ping и другие протоколы, и маршрут для него не
ставится.

```
--- Domains
!telemetry.vendor.example     # с этого компьютера не разрешено
!*.metrics.vendor.example

--- CIDR
!10.20.0.0/16

--- IP
!203.0.113.9

--- Windows
!telemetry.exe
```

**Что такое запрет и чем он не является.** Это ручное правило: вы называете
назначение, и оно перестаёт быть доступным с этого компьютера. Это не
блокировщик рекламы и не блокировщик трекеров. NetRuleRouter не поставляет
списков блокировки, не ведёт их и не заглядывает внутрь страницы — он не может
убрать элемент и не может тронуть то, что отдаётся с того же домена, что и
окружающий контент. Запрет по имени к тому же зависит от того, видим ли мы
разрешение имени: браузер со своим шифрованным DNS (DoH/DoT) способен пройти
мимо такого правила — см. [Что меняет маршрутизация, а что нет](what-routing-changes.md).
Запрет адреса или подсети от имён не зависит.

Ключевые свойства:

- `!` пишется вплотную к значению: `! example.com` с пробелом — ошибка строки,
  как и `?!example.com`: проверка к запрету неприменима.
- **Файл не важен.** Запрет останавливает назначение, где бы он ни стоял — в
  `rules_primary.txt` или в `rules_secondary.txt`.
- `!` работает в любой секции: `Zones`, `Domains`, `IP`, `CIDR`, `Ranges` и
  секции приложений (`Windows` / `Linux` / `MacOS`). Запрещённое приложение
  никуда не подключается.
- Выключается запрет как любое правило — `# !telemetry.vendor.example`
  остаётся в файле, но не действует.
- Совпавший запрет останавливает подключение на своём уровне (§1.5); ни более
  низкий уровень, ни маршрут по умолчанию уже не рассматриваются.
- **Запрет адреса сильнее любого другого правила для этого адреса.** Сайт, имя
  которого вы направили по маршруту, всё равно останавливается, пока он
  отвечает с запрещённого вами адреса.
- **Запрет приложения сильнее любого адресного правила.** Запрещённое
  приложение останавливается даже там, куда другое правило направляет
  назначение по имени или адресу.
- **При равенстве побеждает запрет.** Если запрет и маршрут одинаково узко
  называют одно и то же назначение — даже из разных файлов, — назначение
  запрещается. Экран «Перекрытия» показывает такие пары.
- **Более узкий маршрут оставляет общий адрес открытым.** Если сайт, который вы
  направили более узким правилом, делит адрес с сайтами под более широким
  запретом, этот адрес остаётся доступным — а с ним и те сайты. Экран
  «Перекрытия» перечисляет такие случаи для применённых сейчас правил.
- В приложении выберите маршрутом правила **Запретить**; фильтр списка правил
  **Запрещённые** показывает все запреты.

### 1.13 Правила, добавленные приложением (`--- Auto`)

Некоторые правила добавляются самим NetRuleRouter, а не набираются
пользователем — например, когда сайту, который вы маршрутизировали, нужны
дополнительные хосты для работы конца в конец. Те правила живут в собственной
секции, чтобы вы всегда могли отличить их от своего списка, пересмотреть их и
удалить.

```
--- Auto
rr3.example-cdn.net  # auto:site-companion anchor:example.com added:2026-07-31
*.assets.example.net  # auto:site-companion anchor:example.com added:2026-07-31 все хосты активов
# stale.example.net  # auto:user-confirmed anchor:example.com added:2026-01-05
```

Ключевые свойства:

- **Значения следуют грамматике `--- Domains`** (§1.8): голое имя хоста —
  точный FQDN, `*.example.com` — суффиксный домен. Секция разделяет
  *авторство*, а не типы совпадения — правило, добавленное приложением,
  маршрутизируется точно как эквивалентное правило в `--- Domains`, файлом, в
  котором оно живёт.
- **Каждая строка несёт причину.** Встроенный комментарий начинается с трёх
  структурированных токенов, за которыми следует дополнительный свободный
  текст, который показывается как метка правила, как и любой другой встроенный
  комментарий:

  ```
  # auto:<reason> anchor:<hostname> added:<YYYY-MM-DD>
  ```

  | Токен | Значение |
  |---|---|
  | `auto:<reason>` | Почему было добавлено правило — одна из причин ниже. |
  | `anchor:<hostname>` | Сайт или программа, для которых было добавлено правило. |
  | `added:<YYYY-MM-DD>` | Дата, когда оно было добавлено. |

Токены могут появляться в любом порядке. Интерфейс показывает переведённое
предложение для причины и якоря, а не сырые токены.
- **Причины.** Три определены:

  | Причина | Значение |
  |---|---|
  | `site-companion` | Хост, который нужен якорному сайту, чтобы работать. |
  | `vpn-client-bootstrap` | Адреса, которые VPN-клиенту нужны для переподключения. |
  | `user-confirmed` | Предложение, которое вы приняли. |

Причина, которую эта версия не узнаёт, сохраняется без изменений при проходе
туда-сюда, так что файл, написанный более новой сборкой, никогда не
повреждается более старой.
- **Весь обычный синтаксис применяется.** Комментируйте строку, чтобы отключить
  правило (§1.3), поставьте `!` перед значением, чтобы запретить вместо
  маршрутизации (§1.12), отредактируйте или удалите строку вручную — секция — это простой
  текст, как и всё остальное.
- **Строка без токена `auto:` всё ещё правило.** Она импортируется как обычное
  правило маршрута того файла и сообщается как предупреждение, никогда не выброшена и
  никогда не рассматривается как ошибка. Ручное редактирование этой секции не
  может потерять правила.

### 1.14 Маршрутизация другого VPN-клиента через публичный VPN

Частый вопрос: вы уже маршрутизируете трафик через публичный VPN и хотите,
чтобы через то же подключение выходил *другой* VPN-клиент — например,
корпоративный. Сделать это можно двумя способами. Назначьте публичный VPN
**основным маршрутом** — тогда весь трафик машины по умолчанию пойдёт через
него, без дополнительных правил. Либо оставьте публичный VPN
**дополнительным маршрутом**, настройте поведение по умолчанию (§1.5) так,
чтобы несовпавший трафик уходил через дополнительный маршрут, и добавьте
правило приложения для исполняемого файла другого клиента в секциях
приложений (§1.8, `Windows` / `Linux` / `MacOS`).

В этом правиле укажите исполняемый файл **другого** клиента — никогда не
клиента, чей собственный туннель уже служит маршрутом. Направление клиента в
его же туннель — это петля, а не цепочка.

Прежде чем так настраивать, стоит знать одну вещь: это VPN внутри VPN.
Двойное шифрование заметно снижает скорость, а корпоративный VPN-клиент
может отказаться подключаться вовсе, если обнаружит, что работает через
другой туннель.

### 1.15 Проверить, где работает (`?`)

Некоторые сайты в одном месте открываются через один маршрут, а в другом нет,
и заранее не всегда понятно, какой случай ваш. Знак **`?`** перед правилом
означает: идти через маршрут этого файла, пока сайт через него открывается;
если не открывается, а через другой маршрут открывается, — предложить
перенести правило туда.

```
--- Domains
?accounts.example.com      # страница входа
?*.mail.example.net

--- IP
?203.0.113.7
```

Основные свойства:

- **Сайт начинает там, где вы его записали.** В файле основного маршрута — на
  основном, в файле дополнительного — на дополнительном, пока он там
  открывается.
- **Без вас ваши файлы не меняются.** Если сайт не открывается через свой
  маршрут, а через другой открывается, приложение сразу пускает его через
  другой маршрут и спрашивает, перенести ли правило насовсем, — одним
  уведомлением для всех таких сайтов. **Перенести** переписывает строки в
  другой файл без `?`. **Пока не надо** оставляет файлы как есть: сайт идёт
  через другой маршрут до перезагрузки компьютера, после неё проверка
  повторяется.
- **Проверяется только то, чем вы пользуетесь.** Сайт, который вы не
  открываете, сохраняет свой `?` и не проверяется.
- **Доменные правила и отдельные адреса.** Префикс читается в `--- Domains`
  (и в `--- Auto`, у которой та же грамматика, §1.13), и у точных хостов, и у
  правил-суффиксов `*.`, а также у отдельного IPv4-адреса в `--- IP`. У
  IPv6-адреса `?` снимается с предупреждением, и правило работает без проверки. У `example.*` `?` снимается с предупреждением, и
  правило работает без проверки: проверке нужен один хост. В любой другой
  секции `?` — часть значения, и значение становится невалидным.
- **Не вместе с запретом.** «Проверить, где работает» и «не пускать»
  противоречат друг другу, поэтому `?!значение` — ошибка строки.
- **Отключается как любое правило** — закомментируйте строку:
  `# ?accounts.example.com`.
- **Одно правило на сайт в файле.** `?accounts.example.com` и
  `accounts.example.com` в одном файле — одно и то же правило; остаётся
  строка без `?`.

### 1.16 Применить правило вопреки защите (`+override`)

Запрет или правило дополнительного маршрута, которое захватило бы нужную
системе программу — системную папку, папку, общую для многих программ,
критичный системный процесс (§1.8, Системные программы), — не применяется.
Если вы действительно этого хотите, допишите **`+override`** после значения:

```
--- Linux
!/var/www/* +override      # не пускать программы сайта в сеть
```

Главное:

- **Это заявка, а не разрешение.** Правило остаётся неприменённым с отметкой
  «нужно ваше подтверждение», пока вы не подтвердите его в списке правил окна
  или в терминале. Правка файла ничего не подтверждает.
- **Видно, что правило захватит.** Подтверждение показывает, сколько программ
  под правилом, какие среди них системные процессы и служебные учётные
  записи, программы других пользователей и что может перестать работать —
  получение адреса (DHCP), имена (DNS), время, обновления, вход в домен.
  Подтверждаете, набрав значение правила.
- **На выбранный срок.** 1 час, 1 день (по умолчанию), 1 неделя или до отмены.
  Срок переживает перезапуск; когда он заканчивается, защита снова удерживает
  правило, и вам об этом сообщают.
- **Права администратора там, где правило выходит за ваши программы.**
  Правило, которое захватывает системные папки или процессы, служебные учётные
  записи или программы других пользователей, подтверждает администратор.
- **Видно, пока действует.** В списке правил у правила метка «Разрешено
  вопреки защите» с оставшимся временем, по ней есть фильтр, а подтверждение
  отзывается одним действием. Появился новый критичный процесс под правилом —
  нужно подтвердить снова.
- **Снимается аварийным сбросом сети.** Восстановление сети отзывает все
  подтверждения. Так же действует серия сбоев службы подряд, и вам об этом
  сообщают: разрешённое правило, которое раз за разом роняет службу или сеть,
  не возвращается при каждом перезапуске.
- **Не для всего.** Корень диска и собственные программы приложения
  подтвердить нельзя; `+override` там ничего не меняет.
- **Только правила программ.** В любой другой строке флаг ничего не значит и
  отбрасывается, как `+children`.

## 2. Формат экспорта настроек (YAML)

### 2.1 Обзор

Экспорт настроек — это файл YAML, который захватывает полную конфигурацию
пользователя для резервной копии или передачи на другую установку. Он
записывается, когда пользователь выбирает «Экспортировать настройки», и
читается, когда он выбирает «Импортировать настройки».

Этот раздел документирует границу данных и структуру.

### 2.2 Что включено

- Привязка адаптеров: системный ID, пользовательская метка, статус
  подтверждения.
- Пути файлов правил (не содержимое файла правил — только пути).
- Параметры поведения: режим маршрута, поведение изменения файла, опция
  дочернего процесса.

### 2.3 Что НЕ включено

- Фактическое содержимое файлов правил — это отдельные файлы по сохранённым
  путям.
- Настройки интерфейса (тема, язык, доступность, метки отображения маршрута,
  переключатели отображения) — зависящие от устройства, перенесённые на каждое
  устройство при миграции.
- Внутренние метаданные ревизии (ID ревизии, хэши содержимого, события аудита).
- Состояние runtime, зависящее от устройства (пробы подключения, внешний IP,
  логи).

### 2.4 Структура

```yaml
nrr_settings_export:
  version: 1
  exported_at: "2026-04-18T12:00:00Z"

  adapters:
    primary:
      system_id: "mac=AA:BB:CC:DD:EE:FF;ifindex=3"
      user_label: "Основная сеть"
      user_confirmed: true
    secondary:
      system_id: "mac=11:22:33:44:55:66;ifindex=7"
      user_label: "VPN"
      user_confirmed: true

  rules_files:
    primary: "C:\\Users\\user\\AppData\\Local\\NetRuleRouter\\rules_primary.txt"
    secondary: "C:\\Users\\user\\AppData\\Local\\NetRuleRouter\\rules_secondary.txt"

  behavior:
    route_mode: "prefer-primary"
    file_change_behavior: "notify"
    include_child_processes: false
```

Настройки интерфейса (тема, язык, доступность, метки отображения маршрута)
зависят от устройства и намеренно **не** включены в экспорт — это состояние
переноса на каждое устройство, а не часть переносимой конфигурации.

### 2.5 Системный ID адаптера

Поле `system_id` использует составной формат
`"mac=AA:BB:CC:DD:EE:FF;ifindex=N"`. Этот ключ стабилен на одном устройстве.
При импорте на другое устройство интерфейс представляет диалог выбора адаптера,
если сохранённый ID не найден.

### 2.6 Обработка пути файла правил при импорте

Если путь файла правил в экспорте не существует во время импорта, интерфейс
представляет диалог с тремя вариантами:

1. **Обзор файла** — поиск файла по новому пути.
2. **Пропустить** — начать с пустыми правилами для этого маршрута.
3. **Отмена** — отменить импорт полностью.

### 2.7 Эволюция схемы

Будущие версии могут расширить структуру YAML дополнительными полями; поле
`version` позволяет читателям выявлять и обрабатывать различия схемы.

## 3. Файлы пресетов

### 3.1 Обзор

Пресет — это общий снимок правил маршрутизации. Это позволяет пользователям
экспортировать свои текущие правила и поделиться ими с другими, или
импортировать набор правил, подготовленный сообществом. Пресеты используют тот
же простой текстовый формат, что и рабочие файлы правил (раздел 1).

Пресет состоит из **двух файлов**, по одному на маршрут:

| Имя файла | Содержимое |
|---|---|
| `rules_primary.txt` | Правила для основного маршрута |
| `rules_secondary.txt` | Правила для дополнительного маршрута |

Любой файл может быть опущен, когда маршрут не имеет правил для обмена.

### 3.2 Метаданные пресета

Метаданные пресета сохраняются как комментарии заголовка в верхней части
каждого файла, перед любыми заголовками секций. Все ключи опциональны.

```
# NetRuleRouter пресет — версия 8
# name: Корпоративные правила VPN
# description: Маршрутизирует корпоративный трафик через дополнительный интерфейс (VPN)
# author: Иван Иванов
# preset_version: 1
```

Первая строка `# NetRuleRouter пресет — версия 8` определяет файл как
пресет и несёт версию формата. Файл без этого заголовка всё ещё допустим как
файл правил; строки метаданных рассматриваются как свободные комментарии.

### 3.3 Импорт и экспорт

**Экспорт:** пользователь сохраняет правила каждого маршрута в отдельный файл.
Интерфейс пишет и читает каждый файл независимо.

Интерфейс предлагает параметр «Импортировать оба файла вместе» (по умолчанию
отключено). Если включено, выбор файла для одного маршрута автоматически
открывает диалог выбора файла для другого маршрута.

**Импорт:** импортируемый файл заменяет правила для выбранного маршрута.
Маршрут, чей файл не был выбран, остаётся неизменным. Импорт всегда проходит
через контролируемый поток импорта: парс → валидация → канонизация →
кандидат → диалог пересмотра → активация.

### 3.4 Пак сообщества пресетов

Пак сообщества — это папка (или архив `.zip`), содержащая до двух файлов правил
и человекочитаемое описание:

```
my-corporate-pack/
├── README.txt           # описание свободной формы, заметки об использовании
├── rules_primary.txt    # опционально
└── rules_secondary.txt  # опционально
```

Пользователь загружает папку или архив, извлекает его, открывает нужный файл в
диалоге импорта и импортирует его. Никакой специальный механизм импорта пака не
требуется.

Пресеты сообщества могут быть внесены в официальный репозиторий через pull
request, добавляющий папку пака в `presets/<код-страны>/` или в категорию вроде
`presets/abroad/`, следуя тому же процессу, что и вклады файлов локали.
См. `presets/README.md` для рекомендаций.
