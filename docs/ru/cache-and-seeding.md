# Кэш FQDN/IP и как он заполняется

[English](../en/cache-and-seeding.md)

NetRuleRouter маршрутизирует трафик по домену, зоне, точному IP или
приложению — но уровень фильтрации Windows, через который применяется
политика, понимает только IP-адреса. Чтобы превратить доменное правило
(«направлять `*.bank.com` через primary») в то, что реально можно применить,
службе нужно знать, на какие IP-адреса сейчас резолвится подходящее имя
хоста. Это сопоставление и есть **кэш FQDN/IP**.

## Что это такое

Кэш — это локальная база SQLite, `nrr_fqdn_ip_cache.db`, которую читает и
пишет фоновая служба. Для каждого имени хоста в ней хранится один или
несколько связанных адресов (IPv4 и IPv6), а также служебная информация о том, откуда
взялось каждое сопоставление и насколько оно свежее.

Для понимания кэша важны два свойства:

- **Он строится для хостов, которые называют ваши правила.** Служба не
  строит универсальный DNS-кэш всего, что происходит на машине. Имена других
  сайтов всё же могут в нём оказаться, если они делят адрес сервера с
  направленным сайтом, поэтому кэш общий для компьютера, а его просмотр
  ограничен (см. ниже).
- **Кэш полностью восстанавливаем.** Если файл будет удалён, повреждён или
  вы просто захотите начать с чистого листа, служба соберёт его заново с
  нуля при следующем запуске. Ничего не теряется, кроме необходимости
  заново «выучить» сопоставления — а это происходит автоматически.

## Как он заполняется

У кэша четыре независимых источника. В обычном использовании большинство
записей приходят из первых двух — два оставшихся существуют, чтобы закрывать
конкретные пробелы.

### 1. Живое наблюдение за DNS

Пока служба работает, она следит за разрешением имён на компьютере. Когда
программа резолвит имя хоста, подпадающее под правило вошедшего пользователя,
полученные IP-адреса записываются в кэш. Это основной, всегда
включённый источник, не требующий настройки — так кэш остаётся актуальным для
сайтов, которые вы реально посещаете, пока NetRuleRouter активен.

### 2. Сайты, открытые без запроса имени через службу

Если программа обратилась к адресу, не спросив перед этим имя у службы, служба
всё равно может узнать, какому сайту принадлежит адрес, и ваши правила его
узнают. Такие запросы уходят только к DNS-серверу, настроенному для вашего
соединения; сторонним сервисам ничего не отправляется. Они делаются, только
пока включены предложения правил или защита от утечки, и никогда — для сайта,
который закрыло ваше правило запрета; когда то и другое выключено, их нет.

### 3. Засев из истории браузера (опционально)

Живое наблюдение видит только имена хостов, резолвленные *пока служба
работает*. Сайт, который вы посещали раньше — до запуска службы, или тот,
что до сих пор закэширован в самом браузере с прошлой сессии — не порождает
свежий DNS-запрос, и поэтому может отсутствовать в кэше в первый момент,
когда он понадобится.

Засев из истории браузера закрывает этот пробел: он читает уникальные имена
хостов, уже присутствующие в локальных базах истории ваших браузеров, и
резолвит те из них, что подпадают под ваши активные правила — не дожидаясь,
пока вы посетите их снова. Он доступен на экране «Диагностика» и может быть
запущен **вручную**, либо включён так, чтобы срабатывать **автоматически
при каждом старте службы**. В любом случае это строго опциональная функция —
из ваших браузеров ничего не читается, пока вы её не включите. На компьютере,
которым пользуются несколько человек, заполнение читает только браузеры того,
кто его запросил, и никогда — историю другого пользователя.

Извлекаются только имена хостов. Полные URL, заголовки страниц, время
посещений и счётчики визитов никогда не покидают машину, а имена хостов, не
подпадающие ни под одно активное правило, немедленно отбрасываются, а не
кэшируются при заполнении, поэтому заполнение не копирует историю ваших
посещений в кэш.

Кэш имён общий для компьютера. Обычный пользователь видит в просмотре кэша
только имена, которые покрывают его собственные правила; администратор видит
все. Очистка кэша требует прав администратора.

#### Поддерживаемые браузеры

**Браузеры на Chromium** — Chrome, Edge, Brave, Яндекс.Браузер, Opera, Opera
GX, Vivaldi и обычный Chromium. Читаются все найденные профили внутри папки
`User Data` браузера (`Default` плюс любые `Profile N`), за исключением
Opera и Opera GX, чей профиль лежит прямо в `%APPDATA%\Opera Software\Opera
Stable` / `Opera GX Stable`, а не внутри папки `User Data`. Для каждого
профиля имена хостов извлекаются из таблицы `urls` файла `History` этого
профиля.

**Браузеры на движке Firefox** — Firefox, LibreWolf и Waterfox. Имена хостов
извлекаются из таблицы `moz_places` файла `places.sqlite` каждого профиля.

**Почта: Thunderbird** — только имена почтовых серверов его учётных записей,
из файла `prefs.js` каждого профиля. Больше из файла ничего не сохраняется:
как и браузеры, он даёт только имена хостов.

**AI-браузеры (best-effort)** — Arc для Windows и Perplexity Comet, оба на
Chromium. Arc распространяется в виде MSIX-пакета, поэтому его профиль
находится сканированием пути
`%LOCALAPPDATA%\Packages\TheBrowserCompany.Arc_*\LocalCache\Local\Arc\User Data`,
а не фиксированной папки вендора. Comet проверяется в двух возможных местах
внутри `%LOCALAPPDATA%` — `Perplexity\Comet\User Data` и `Comet\User Data`,
поскольку расположение установки менялось от релиза к релизу. Честно говоря,
поддержка этих двух браузеров — **best-effort**: оба являются молодыми,
быстро меняющимися браузерами, чья структура данных на диске меняется
быстрее, чем документируется, поэтому указанные выше пути могут устареть
после очередного обновления. Если Arc или Comet перестал добавлять хосты в
кэш, пожалуйста, сообщите нам любым удобным способом — через GitHub Issues
проекта (<https://github.com/kroxiksut/net-rule-router/issues>) или
Telegram-канал (<https://t.me/netrulerouter>). Строка лога
службы `browser-history discovery finished` перечисляет, какие источники
реально были найдены на вашей машине, и именно эту строку стоит приложить
как доказательство.

Каждый из этих браузеров держит свою базу истории открытой — и
заблокированной — пока работает, поэтому NetRuleRouter никогда не открывает
живой файл напрямую. Сначала он копирует базу во временный файл и читает
именно эту доступную только для чтения копию, а затем удаляет копию.
Браузер, который не установлен, либо чью базу не удалось скопировать или
прочитать по любой причине, просто пропускается — засев продолжается с
теми браузерами, что доступны.

#### Tor Browser не поддерживается

Tor Browser сознательно исключён по двум независимым причинам, каждой из
которых было бы достаточно самой по себе:

- По умолчанию Tor Browser работает в режиме постоянной приватности и
  вообще не сохраняет историю посещений на диск, поэтому читать попросту
  нечего.
- Даже если бы история существовала, это бы не помогло: трафик,
  маршрутизируемый через Tor, никогда не выглядит для Windows как прямое
  соединение с посещённым сайтом — операционная система видит только
  соединения с IP-адресами узлов (relay) сети Tor. Кэширование имени
  хоста, посещённого через Tor, никак не улучшило бы решения о
  маршрутизации NetRuleRouter, потому что реальный сетевой путь вообще не
  затрагивает настоящий IP этого имени.

### 4. Файл hosts

Файл `hosts` операционной системы
(`%SystemRoot%\System32\drivers\etc\hosts`) сопоставляет имена хостов с IP
ещё до того, как ваш трафик доходит до NetRuleRouter, и NRR никогда его не
переопределяет. Если для имени хоста из правила есть запись в `hosts`,
служба показывает это как информационную пометку — чтобы было видно, когда
именно запись `hosts`, а не DNS, определяет, во что резолвится имя. Это
помогает объяснить поведение правила, которое иначе выглядело бы странным.

## Известное ограничение: DNS-over-HTTPS

Живое наблюдение за DNS отслеживает обычный DNS-трафик. Браузер, настроенный
на DNS-over-HTTPS (DoH), отправляет свои запросы внутри зашифрованного
HTTPS-соединения — служба не может увидеть или разобрать такой трафик,
поэтому хосты, резолвленные таким способом, никогда не порождают запись в
кэше через живое наблюдение. Два описанных выше средства смягчения
существуют во многом именно из-за этого: засев из истории браузера
заполняет кэш заранее, независимо от того, как браузер резолвил имя, а
локальный DNS-резолвер (способ маршрутизации по умолчанию) может перехватывать и наблюдать запросы
напрямую.
